# ТЗ: совместная работа с Cloud Web и неизменность задания

**Область:** только приватный `arwoxbx24/eurosteklo`.
**Дата и источник:** 2026-09-30, прямое поручение владельца в текущей сессии;
проверенные Git-факты — [аудит](../research/2026-09-30-codex-session-audit.md).
**Статус:** одноразовый паспорт этой задачи. Текст замораживается после приёмки;
во время выполнения его не редактируют. Новые требования оформляются отдельным
поручением и паспортом с новой областью, без ретроспективного исправления этого.
Этот документ дополняет действующие П1–П11 Git-регламента, но не даёт права
менять клиентский процесс, Битрикс24 или старую спецификацию.
Устаревшие снимки веток, статуса метки и default внутри П1–П11 не применяются
вместо свежих GitHub-фактов: аудит фиксирует их противоречия с текущим состоянием.

## 1. Деловая цель и результат

**REQ, владелец 30.09:** Codex CLI, Claude CLI и Cloud Web должны видеть
принятые данные проекта, сохранять собственную незавершённую работу и иметь
проверяемую историю и откат. Перед новой работой агент должен знать о коммитах
Cloud Web, а каждое утверждение о выполнении должно иметь независимый источник.

**PROVEN, аудит §«Состояние GitHub»:** `main` — ветка по умолчанию; Cloud Web
внесла изменения через PR №3, уже слитый в `main@6b89bfec…`. Существующая
`claude/charming-tesla-tmovg4@d1b4bb0…` отстаёт на один merge-коммит. Это
снимок на дату проверки, а не вечное имя web-ветки. **UNVERIFIED:** какой ref
получит следующая web-сессия и почему другие облачные агенты сообщили об ошибке.

**Критерий результата:** новый агент начинает от свежего удалённого `main` либо
безопасно синхронизирует **свою** незавершённую ветку с ним; PR показывает
только разрешённую задачу; после слияния проверены серверный SHA и доступность
принятых файлов из `main`. До этих проверок слово «актуально» не используется.

## 6. Сценарии ошибок и восстановление

- **Web-ветка позади `main`.** Сохранить собственные незакоммиченные правки;
  определить её фактический ref и base; начать новую задачу от свежего
  `main` либо merge свежий `main` в свою ещё открытую ветку. Не делать
  `reset --hard` и не отправлять старый локальный checkout.
- **Две сессии меняют общий файл.** Остановить вторую запись, сохранить оба
  diff отдельно, назначить одного владельца файла; объединять только через
  проверенный PR. Наличие отдельных папок идей не защищает общие файлы.
- **Push/PR отклонён.** Сохранить commit и точную ошибку в своём атоме;
  не менять провайдера, клиент или ref для обхода отказа. Остальные независимые
  проверки продолжить.
- **Неизвестно, где пишет Cloud Web.** Не угадывать по старому имени ветки;
  установить branch/SHA из текущей web-сессии и PR. Пока это не установлено,
  синхронизация с этим сеансом UNVERIFIED.
- **ТЗ требует поправки после фиксации.** Зависимую работу остановить и
  оформить новый вопрос/паспорт; данное ТЗ и его SHA сохранить. Историю
  исправляют новым коммитом только в отдельно разрешённой задаче; исходный
  текст этой задачи не меняют.

## 7. Приёмка, публикация и откат

Перед финалом проверяются T01–T08 и три круга проектного закона:
источник каждого утверждения, отсутствие противоречий с действующими
документами и проверка критиком. Неизвестное остаётся явным, а не превращается
в `PASS`. ТЗ не считается «технически неизменяемым»: `main.protected=false` и
серверные rulesets недоступны на текущем плане (аудит §«Состояние GitHub»).

Принятое содержимое попадает в `main` через собственный PR. Его полный SHA и
ссылка записываются в Beads. Откат только новым `git revert` через PR;
прошлый SHA и этот документ не переписываются. `client-materials/private/`,
CRM, чужие worktree и ветки в этой процедуре не участвуют.
