**Создана**: 30.09.2026 Codex CLI (PR №1, коммит `eff23fb`) · **Доработана**: Claude Web 30.09.2026 по итогам проверки · **Основание**: запрос владельца о совместной работе трёх агентов (Codex CLI, Claude CLI, Claude Web): разные ветки, у всех актуальные данные, общий мозговой штурм, точки отката, сохранение истории; решение владельца 30.09: «выбрать лучшее архитектурное решение, не останавливаться».
**Статус**: действует.

## Цель и границы

Цель — дать трём изолированным агентам, работающим в разное время, одну общую проверяемую версию, место для общих гипотез и возможность вернуться к принятому состоянию, ничего не ломая.

- Правило относится только к репозиторию `arwoxbx24/eurosteklo` (закон жёсткого контура): его не выносят и не масштабируют на другие проекты. Битрикс24 не затрагивается.
- В Git хранятся только разрешённые обезличенные материалы и производные документы. `client-materials/private/`, выгрузки CRM, секреты и база Beads в Git не попадают и ветками не синхронизируются (П10). Из одного `git pull` не следует, что локальные каталоги на разных машинах одинаковы.
- Регламент касается только Git. Изменение клиентских документов по-прежнему идёт по закону ТЗ и RG-001 (П11).

## Решение

```
  docs/idei/codex/  docs/idei/claude-cli/  docs/idei/claude-web/   (каждый пишет в свою, читают все)
            \                 |                  /
  codex/<атом>-x        claude/<атом>-y             claude/<имя-от-платформы>
   (сессия Codex CLI)    (сессия Claude CLI)        (сессия Claude Web)
            \                 |                  /
             PR → merge-коммит (только в одну сторону: ветка → main)
                              v
  main ──●──────●──────────●──────────●──►  (история только дописывается)
         575a157            \
         checkpoint/2026-09-30-lidy-sdelki  + строка в docs/CHECKPOINTS.md
                              |
  codex/8b44-eurosteklo ──── архив на 575a157; в него не пишут
```

**П1. Ствол.** `main` — единственная общая ветка и ветка по умолчанию на GitHub. `codex/8b44-eurosteklo` и старые ветки сессий остаются архивом: в них не пишут, их не перематывают и не удаляют без отдельного решения владельца.

**П2. Ветка на сессию.** Каждая сессия — своя ветка от свежей `origin/main`. Имена: Codex — `codex/<атом>-<суть>`; Claude — `claude/<атом>-<суть>` или выданная платформой ветка `claude/<имя>`. Если платформа выдаёт имя сама, оно не означает совместное владение веткой. В чужую ветку не пишет никто. Автор коммитов — своё имя в своём клоне: `Codex CLI`, `Claude CLI` или `Claude Web`; проверяют фактические метаданные коммита, а не предполагают автора по префиксу.

**П3. Начало сессии.** Проверить своё незавершённое дерево через `git status` → `git fetch origin` → создать отдельную ветку и рабочее дерево от `origin/main` (если своя ветка не закончена — синхронизировать её с `origin/main` после проверки изменений). Для Codex отдельный worktree обязателен. Прочитать `AGENTS.md`, `docs/ppo/HANDOFF.md`, журнал решений (`docs/ppo/00-resheniya-vladeltsa.md`), `docs/CHECKPOINTS.md`, свежие файлы `docs/idei/*/`.

**П4. Конец сессии.** Проверки: `git diff --check`; поиск ПДн (телефоны, e-mail, фамилии) = 0; если трогали `docs/ppo` — `python3 docs/ppo/build_all.py`. Затем push своей ветки → PR в `main` → слияние merge-коммитом (не squash, не rebase) после обязательных проверок → запись в `docs/CHECKPOINTS.md`, если закрыт этап. Исключение: изменения клиентских документов (`docs/ppo/**`, кроме `HANDOFF.md`; ТЗ; карты) сливаются только после «да» владельца, до этого PR остаётся открытым. Идеи и служебные файлы агент сливает сам.

**П5. Мозговой штурм.** Папки `docs/idei/codex/`, `docs/idei/claude-cli/`, `docs/idei/claude-web/`: каждый агент пишет только в свою, читают все. Файл `ГГГГ-ММ-ДД-<тема>.md`; в шапке — статус ИДЕЯ | ГИПОТЕЗА | ПРИНЯТО ВЛАДЕЛЬЦЕМ | ОТКЛОНЕНО, источники, метки PROVEN/INFERRED/UNVERIFIED по закону блокировки. Отклик на чужую идею — файлом в своей папке со ссылкой на неё. Идеи попадают в `main` сразу (их видят все), в клиентские документы — только после «да» владельца.

**П6. Общие файлы.** `AGENTS.md`, `CLAUDE.md`, `docs/ppo/HANDOFF.md`, `docs/ppo/00-resheniya-vladeltsa.md`, `client-materials/sanitized-*.md`, `docs/ppo/_common/`, `docs/CHECKPOINTS.md` в каждый момент правит одна сессия; журнал решений и реестр точек — только дописываются. Конфликт в собранных HTML решается в `_parts/` с пересборкой `python3 docs/ppo/build_all.py`; HTML вручную не склеивают.

**П7. Дробление внутри сессии.** Параллельные блоки одной сессии (закон дробления) пишут разные файлы в принадлежащем этой сессии рабочем дереве. Двум разным сессиям писать в одну ветку или одно дерево запрещено. Codex всегда использует отдельный `git worktree`; остальные агенты также изолируют своё дерево при совместной работе на одной машине.

**П8. Точки отката.** Реестр `docs/CHECKPOINTS.md` (дата, метка, полный SHA, что утверждено) + аннотированная метка `checkpoint/<ГГГГ-ММ-ДД>-<этап>` на утверждённый коммит. Метки не двигают и не удаляют; при сомнении сверяют полный SHA из реестра с удалённым Git (метка без серверной защиты — навигация, не резерв). Откат — только `git revert` новым PR. Force-push и переписывание истории `main` запрещены; исключительные случаи с персональными данными рассматриваются отдельно по решению владельца.

**П9. Старые локальные копии** (история до чистки 29.09): ничего из них не пушить и не вливать; `reset --hard`, cherry-pick и автоматический merge не применять. Порядок: проверить `git status`, сохранить незавершённую работу локально без публикации старой истории, выполнить `git fetch origin`, создать новое отдельное дерево от `origin/main` и переносить только проверенные изменения без ПДн.

**П10. Вне Git.** `client-materials/private/`, база Beads, выгрузки CRM, ключи. Git их не синхронизирует; передаёт владелец отдельно. Beads — рабочий инструмент Codex CLI, для Claude не обязателен; источник истины о состоянии — репозиторий (`HANDOFF`, `CHECKPOINTS`).

**П11. Границы регламента.** Регламент касается только Git. Изменение клиентских документов идёт по закону ТЗ и RG-001 (spec 001): ТЗ → `/ce-doc-review` → `code-channel`; Git — транспорт, а не замена этому порядку. Законы `CLAUDE.md` и `AGENTS.md` (дробление, согласование, жёсткий контур, блокировка) действуют без изменений.

## Порядок сессии (шпаргалка)

```bash
# начало: проверить свою работу и получить свежий main
git status
git fetch origin
# создать свою ветку и отдельное дерево от origin/main по правилам агента
# конец: проверить изменения, секреты, ПДн и обязательные проверки
git diff --check
python3 docs/ppo/build_all.py  # только если трогали docs/ppo
git push -u origin HEAD
# PR в main → слияние merge-коммитом (клиентские документы — после «да» владельца)
# утверждённый этап → строка в docs/CHECKPOINTS.md и аннотированная метка на его SHA
```

## Открытые вопросы владельцу (действия только владельца)

1. Запрос в поддержку GitHub об удалении недоступных из веток коммитов `fd1bbeb9649a…` и `7544309` (и кэшированных представлений) — по предыдущей проверке в них файл сотрудников с полными ФИО. Исполнение запроса в поддержку здесь не подтверждено.
2. Защита `main` на 30.09.2026 имеет `protected=false`; доступность серверных правил защиты веток и меток на тарифе не подтверждена. Решение о включении защиты остаётся за владельцем репозитория.

Справка по механике: [git worktree](https://git-scm.com/docs/git-worktree) — несколько рабочих деревьев одного репозитория; [git revert](https://git-scm.com/docs/git-revert) — отмена изменений существующего коммита новым коммитом; [GitHub protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches) — запрет force push и удаления при включённом правиле (в «Евростекле» не включено, см. таблицу состояния).
