# Спецификация совместной работы в Git — «Евростекло»

Дата: 30.09.2026. Основание: запрос владельца в текущей сессии о работе Codex, Claude Web и Claude CLI, сохранении истории и точках отката. Статус: проект правила для согласования и завершения Claude Web; изменение ветки по умолчанию и перенос чужой работы ещё не выполнены.

## Цель и границы

Цель — позволить разным сессиям готовить документы одновременно или по очереди, сохраняя проверяемую общую версию и возможность вернуться к принятому состоянию. Это правило относится только к репозиторию `arwoxbx24/eurosteklo`. Оно не разрешает менять Битрикс24, перестраивать исходники клиента, публиковать персональные данные или сливать неподтверждённые выводы в клиентские документы.

В Git хранятся только разрешённые обезличенные материалы и производные документы. `client-materials/private/`, выгрузки CRM, секреты и локальная база Beads не становятся общими от создания веток: их целостность и разрешённый способ передачи проверяются отдельно. Полная одинаковость локальных каталогов на разных машинах из одного `git pull` **не следует**.

## Решение по архитектуре

1. **Одна общая ветка `main`** — место для принятых обезличенных документов. Сейчас это подготовленная ветка, а не утверждённая ветка по умолчанию. Переход завершается только после проверки открытых работ и смены default в GitHub отдельным шагом.
2. **Одна ветка и отдельная рабочая копия на задачу или сессию**, например `codex/<атом>-<суть>` и `claude/<атом>-<суть>`; локально рабочие копии оформляются через worktree. Web и CLI одного поставщика при одновременной работе получают разные ветки. Префикс обозначает владельца изменений, а не общий канал записи. Если веб-платформа выдаёт случайную ветку, её считают временной рабочей веткой и не сливают автоматически в другую ветку агента; доступные операции веб-платформы нужно проверить в её сессии.
3. **Обмен через PR в `main`**: агент публикует только свою ветку, проверяет точный коммит, источники, конфиденциальность и применимые проверки. После принятия PR следующая сессия обновляет свою ветку от свежей `main` и разрешает конфликты в своих файлах. Простое получение изменений из `main` не делает ветку автоматически принятой.
4. **Гипотезы отделяются статусом и происхождением, а не только каталогом.** Отдельные папки могут снизить пересечение при редактировании, но не гарантируют отсутствия конфликтов в оглавлении, сборке и общих документах. Неподтверждённый бизнес-процесс не переносится в клиентское ТЗ. По правилу проекта без источника фиксируются «Информации нет» и вопрос клиенту; `INFERRED` требует два источника.
5. **Одна запись в общий файл в каждый момент**: два агента не редактируют одно рабочее дерево и не отправляют коммиты в один и тот же удалённый ref. Для общего файла владелец задачи определяется в Beads; разные PR могут существовать параллельно, а конфликт разрешается до слияния следующего PR.

### Почему не две постоянные ветки `Codex` и `Claude`

Такое деление изолирует поставщиков друг от друга, но Claude Web и Claude CLI всё равно конкурируют за один `Claude` ref; аналогично Codex Web и Codex CLI — за один `Codex` ref. Повторное двустороннее слияние длинных веток накапливает конфликты и делает источник принятой версии неочевидным. Третья ветка `main` нужна как место интеграции, а рабочие ветки лучше привязывать к конкретной задаче и сессии. Слияние выполняется в одном направлении: задача → `main`; новая задача начинается от актуальной `main`.

## Порядок работы

1. **Перед началом.** Проверить проект, свой атом Beads, текущую ветку, статус файлов и активные рабочие деревья. Получить удалённые ссылки. Новую ветку создать от актуальной `origin/main` в отдельном worktree. Не переключать чужое дерево и не переносить старую историю после очистки 29.09 без отдельной проверки каждого коммита.
2. **Во время работы.** Вносить только ограниченные задачей изменения. К каждому утверждению о процессе прикладывать источник и метку; идеи без источника оставлять вопросами. Коммитить и публиковать свою ветку после проверки на секреты и персональные данные. Проверять, что удалённый коммит совпал с локальным.
3. **Перед объединением.** Обновить сведения о `main`, сравнить точный diff PR, проверить конфликты, ссылки, сборку затронутых документов и применимые CI. Если `main` ушла вперёд, согласовать свою ветку с ней в своём worktree и повторить затронутые проверки. Сливать только проверенный head PR, без прямой записи в `main` и без принудительного push.
4. **После объединения.** Убедиться, что PR имеет статус `MERGED`, а его изменения доступны из удалённой `main`. Зафиксировать коммит и результат в Beads. Другие агенты берут обновлённую `main` при следующем входе. Удалять только собственную слитую ветку по действующим правилам; удаление чужих веток не часть этой задачи.

Для собранных HTML конфликт решается в исходных фрагментах `_parts/`, затем выполняется штатная сборка `python3 docs/ppo/build_all.py` и проверки затронутых страниц. Если меняется общий источник, отдельные папки идей не освобождают от этой проверки.

## Точки безопасности и восстановление

- **Перед переходом** сохранить полные SHA прежней общей ветки и каждого принятого этапа в Beads/PR. Аннотированная метка `checkpoint/<дата>-<этап>` может улучшить навигацию, но без подтверждённой серверной защиты метку можно передвинуть или удалить; сама по себе она не является резервной копией.
- **Обычный откат** принятого изменения: новый PR с отменяющим коммитом (`git revert`), затем те же проверки и merge. Это сохраняет историю и не затрагивает чужие ветки.
- **Старая локальная история после очистки ПДн:** сначала сохранить список собственных незаконченных изменений и проверить их происхождение. Не применять `reset --hard` и не делать автоматический merge/cherry-pick: они могут потерять локальную работу или вернуть закрытые данные. Новую работу начинать от чистой `origin/main`; переносить только вручную проверенные разрешённые фрагменты через отдельный PR.
- **Приватные оригиналы и CRM** требуют отдельного разрешённого хранения, списка файлов, контрольных сумм и резервного восстановления. Git-ветки, теги и PR этого не обеспечивают. Синхронизация Beads тоже отдельна от публикации Git-коммитов.
- **При обнаружении утечки** остановить публикацию и отдельно согласовать удаление/ротацию по факту; исключительный прошлый случай переписи истории не является постоянным разрешением переписывать её снова.

| 5. Цикл | Каждая новая задача имеет свой атом, ветку/worktree и PR; после merge остальные сессии получают свежую `main`. | Проверены remote SHA, статус PR, затронутые файлы и отсутствие незакоммиченных изменений. |

**Открыто до этапа 4:** кто и когда завершает текущие сессии Claude и переводит ветку по умолчанию. Это не мешает вести новые PR в существующую `main`, но не позволяет объявить миграцию законченной.

Справка по механике (проверено 30.09.2026): [Git worktree](https://git-scm.com/docs/git-worktree) описывает несколько рабочих деревьев одного репозитория; [Git revert](https://git-scm.com/docs/git-revert) — отмену изменений существующего коммита; [GitHub protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches) — запрет force push и удаления при включённом правиле. Наличие такой защиты именно в «Евростекле» не подтверждено: проверка API выше дала обратный результат.
