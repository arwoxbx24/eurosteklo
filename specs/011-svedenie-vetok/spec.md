### §1 Бизнес

Запрос — см. «Слово владельца». Ценность: одно место правды (`main`) перед встречей с клиентом и гарантия, что подтверждённое состояние карт можно вернуть в любой момент. Критерий успеха: всё содержимое веток находится в `main`, коммиты сохранены (на GitHub — все, кроме ветки с ФИО, она только локально), точка возврата названа и лежит на GitHub.

### §2 Аналитика

Факты о ветках (01.10):

1. 24 PR (1–20, 22–25) слиты в `main` обычными merge-коммитами — это 23 разных имени веток (PR 2 и 3 шли из одной ветки `claude/charming-tesla-tmovg4`, головы `68268d6` и `d1b4bb0`); все эти ветки на GitHub удалены, их история целиком входит в `main`.
2. `claude/00v-ispravleniya-k-vstreche` слита через squash (PR 21): содержимое в `main`, но её собственный коммит `a4b5124` в историю `main` не входит (`git rev-list --count origin/main..claude/00v-…` → 1). Ветка на GitHub удалена, коммит есть только локально — **риск потери истории**.
3. `codex/8b44-eurosteklo` (локальная): 21 коммит сверх своей удалённой точки; 19 уже есть в `main` по содержимому (`git cherry`), 2 своих (`56f41cb` добавляет, `fd1bbeb` убирает файл со списком сотрудников) взаимно гасятся. В истории этих двух коммитов — версия файла с полными ФИО.
4. Версия файла сотрудников в `main` и в `a4b5124` — blob `3fcb725`, обезличенная (подсчёты ФИО, отчеств, телефонов и почт → 0). Версия с ФИО — blob `f08f5c6`, есть только в `codex/8b44-eurosteklo` (`git branch -a --contains 56f41cb` → одна эта ветка; `git merge-base --is-ancestor 56f41cb a4b5124` и то же для `origin/main` → код 1).

### §3 Архитектура

Решения:

- **Р-1. Единственная ветка — `main`.** Новых слияний содержимого не требуется: всё содержимое уже в `main` (факты 1–3).
- **Р-2. История сохраняется тегами, а не ветками.** Тег неизменяем и не участвует в работе агентов. `archive/claude-00v` → `a4b5124`, отправляется на GitHub.
- **Р-3. Точка отката — тег `stable-2026-10-01`** на `main` после слияния этой спецификации (страницы карты при этом не меняются — md5 из §0; это состояние, предварительно подтверждённое владельцем к встрече), отправляется на GitHub.
- **Р-4. Ветка `codex/8b44-eurosteklo` на GitHub не отправляется** — ни веткой, ни тегом: в её истории полные ФИО (закон проекта: конфиденциальное в Git не попадает). Остаётся локально как есть, не удаляется.
- **Р-5. Откат — только вперёд по истории** (`git revert` через PR). Переписывание истории (`reset --hard`, `push --force`, `rebase` опубликованного) запрещено.

Отвергнуто: слить локальную ветку Codex в `main` (внесёт ФИО в общую историю); пересобрать историю в одну линию (теряет историю, требует force).

### §5 DevOps — выполнение и откат

**Выполнение** (главный агент, по одной команде, один ref на push):

0. Слияние PR этой спецификации в `main`, удаление её ветки на GitHub.
1. `git tag archive/claude-00v a4b5124`; `git tag stable-2026-10-01 <полный sha HEAD main после шага 0>`.
2. Проверка перед отправкой (каждая отдельной командой): `git merge-base --is-ancestor 56f41cb archive/claude-00v` → код 1; то же для `stable-2026-10-01` → код 1; `git rev-list --objects archive/claude-00v stable-2026-10-01 -- client-materials/sanitized-sotrudniki.md` → в выводе нет `f08f5c6`. Не прошла — тег не отправляется.
3. `git push origin archive/claude-00v`; `git push origin stable-2026-10-01`.
4. Сверка публикации: md5 страниц по ссылке = md5 файлов по тегу `stable-2026-10-01`.

**Откат содержимого** (если после встречи понадобится вернуть подтверждённое состояние):

1. Посмотреть, что изменилось: `git log --first-parent --oneline stable-2026-10-01..origin/main` — только коммиты основной линии.
2. Своя ветка от `origin/main`; отменяются только коммиты из этого списка, от новых к старым: с двумя родителями — `git revert -m 1 <коммит>`, с одним (squash) — `git revert <коммит>`. Коммиты внутри веток отдельно не отменяются.
3. Проверка: `git diff --stat stable-2026-10-01 HEAD -- docs/ppo` → пусто (`docs/ppo` — каталог всех страниц карты и архива в репозитории). Конфликт при отмене — стоп, доклад владельцу; частичный откат в `main` не сливается.
4. PR в `main`, merge. История сохраняется: отменённые коммиты остаются в ней.

**Откат публикации** (страницы по прежней ссылке):

1. `git worktree add .worktrees/claude/otkat stable-2026-10-01` — файлы ровно подтверждённого состояния.
2. Перечень объектов — фактический: `mc ls --recursive b244minio/files/20261001-ppo-evrosteklo/`; каждый объект перезаписывается одноимённым файлом из `docs/ppo/` этой рабочей копии (`mc cp` с прежними заголовками: HTML — `Content-Type=text/html; charset=utf-8`, `Cache-Control=no-store`); ссылка не меняется, новых объектов не создаётся.
3. Сверка md5 по ссылке с md5 файлов тега.
4. `git worktree remove .worktrees/claude/otkat`.

**Восстановление удалённой ветки**: любая из 23 — `git branch <имя> <sha головы из её PR на GitHub>` (для общей ветки PR 2 и 3 — голова PR 3, `d1b4bb0`); `00v` — из тега `archive/claude-00v`.

**Негативные примеры (так делать нельзя):**

- `git push --force` или `git reset --hard` для «чистой» истории — история теряется, откат невозможен.
- Отправить `codex/8b44-eurosteklo` на GitHub «для сохранности» — в общую историю попадут полные ФИО.
- Удалить локальную `claude/00v…` до отправки тега `archive/claude-00v`, или удалить локальную `codex/8b44…` без слова владельца (тега для неё не будет) — это единственная копия их коммитов.
- Откат удалением тега или перемещением `stable-2026-10-01` на другой коммит — точка возврата перестаёт быть неизменной; новая точка — новый тег с новой датой.
- Пересборка или правка страниц карты в рамках этой спецификации — состояние подтверждено владельцем, оно не меняется.

## Сценарий и проверка

**История 1 (P1) — точка возврата.** Владелец идёт на встречу с подтверждённым состоянием карт. После встречи материалы меняются. Если изменения окажутся неверными, подтверждённое состояние возвращается по §5 без потери истории.

Проверка независимо: строки 2 и 6 таблицы §7.

**История 2 (P1) — ничего не потеряно.** Коммиты 23 веток, слитых через PR, достижимы из `main`; коммит `00v` — из тега на GitHub. Для ветки с ФИО гарантия уже: её содержимое есть в `main`, а сами коммиты хранятся только локально (Р-4).

Проверка независимо: строки 1, 3, 4, 7 таблицы §7.

### Крайние случаи

- После тега в `main` попал новый коммит — тег не двигается; откат идёт к тегу, новая подтверждённая точка получает новый тег с новой датой.
- Push тега отклонён — причина читается из вывода, тег остаётся локально, повтор той же командой; ветки при этом не трогаются.
- Локальный каталог утрачен — теряется только ветка Codex (Р-4); её содержимое на 19 из 21 коммитов уже в `main`, 2 остальных взаимно гасятся.

## Требования

- **FR-001**: Единственная ветка на GitHub — `main`.
- **FR-002**: Тег `stable-2026-10-01` указывает на `main` после слияния этой спецификации и лежит на GitHub.
- **FR-003**: Тег `archive/claude-00v` указывает на `a4b5124` и лежит на GitHub.
- **FR-004**: Ни ветка, ни тег с историей `codex/8b44-eurosteklo` на GitHub не отправляются.
- **FR-005**: История не переписывается: без force, `reset --hard`, `rebase`.
- **FR-006**: Опубликованные страницы совпадают с файлами тега `stable-2026-10-01`.
- **FR-007**: Порядок отката содержимого и публикации записан командами (§5).
