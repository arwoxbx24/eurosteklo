## §2 Решение (ADR)

**Контекст**: число папок клиентов растёт; ручной паспорт устаревает и забывается (слово владельца). Самописные хуки запрещены (`docs/LAWS-PROCEDURES.md:163-165`).

| Вариант | За | Против | Вердикт |
|---|---|---|---|
| А. Статичный `PASSPORT.md` в каждой папке | Просто | Устаревает, ручное заполнение, забывается — отклонено владельцем | Нет |
| Б. Хук SessionStart печатает сводку | Автоматически при входе | Самописные хуки запрещены законом | Нет |
| В. Правило-конвенция без данных + сводка, вычисляемая при обращении + ежедневная проверка с автозадачами | Нечему устаревать: данные читаются с диска; новая папка ловится проверкой без участия человека | Нужны правки `tools` и общих законов (вне Евростекла) | **Да** |

**Принцип**: в файлах хранится только порядок (как устроено), никогда — состояние (что сейчас). Состояние вычисляется.

## §3 Требования

- FR-1. Правило `clients/` описывает только конвенцию: имя папки = компания; режим `<компания>/` или `<компания>-dev` + `<компания>-prod`; закрытые материалы — `private/` в `.gitignore`; секреты — только `/root/workspaces/secrets/`; перед работой — команда сводки. Ни одной строки с данными конкретного проекта. Одинаково для Claude (`CLAUDE.md`) и Codex (`AGENTS.md`).
- FR-2. Сводка `client-context <папка>` печатает, вычисляя при каждом вызове: свой ли репо и remote; база задач (`bd -C <папка> where`) и открытые задачи; режим dev/prod по `ga_base`; опубликованные ссылки, если в проекте есть реестр ссылок; готовую команду доставки с `BEADS_DIR`, `BEADS_ACTOR` и шаблоном трейлеров. Ничего не пишет. Повторно использует `git-auto-lib` (`ga_roots`, `ga_base`, `ga_repo_of`), а не дублирует их.
- FR-3. Режим `client-context --check <папка>` возвращает список нарушений конвенции FR-1 с кодом выхода ≠0 при нарушениях.
- FR-4. Ежедневная проверка обходит `clients/*`, вызывает FR-3 и заводит задачу bd на каждое новое нарушение — одна открытая задача на (папка, причина), без дублей (образец — `dcfg-sw0b3.1`). Задачи — в общей базе с меткой `contour:clients`.
- FR-5. `ship-post` для вложенного репо со своей `.beads` сам выбирает её базу (без ручных `SHIP_POST_*` и `BEADS_DIR`).
- FR-6. Формат коммита для `--submit` описан в одном месте (`tools/docs/ship-post-ARCHITECTURE.md`); законы и сводка ссылаются на него, а не повторяют.
- FR-7. Механический режим правок: ТЗ на замену текста без изменения смысла содержит готовую программу замен; каждая замена проверяет ровно одно совпадение, иначе файл не пишется. Исполнитель ничего не формулирует сам.
- FR-8. Закон дробления Евростекла: параллельные блоки, меняющие файлы в Git, работают каждый в своём worktree; блоки только чтения могут делить папку.
- FR-9. Таблица уровней csb: механическая замена текста (FR-7) — L1 без стадии 3 ★/ce-plan; план = сама программа замен.
- FR-10. Проверка лимитов до запуска канала покрывает форму 2 (codex). Делается в существующей задаче `eurosteklo-426`, новая не создаётся.

Вне объёма: перенос существующих папок под новую конвенцию (это делают задачи, которые заведёт FR-4); правка 1С и ТЗ клиента; находки Ф1–Ф4 (только строки bd).

## §5 Риски и откат

- Главный риск: U1–U7, U9 меняют общие `tools` и законы — затронут все проекты. Откат: каждая единица — отдельный коммит и PR, `git revert` по SHA.
- U4 заводит задачи автоматически: число задач первого прогона — НЕ ПРОВЕРЕНО (по данным D: 7 папок без своего репо и без инструкций, 1 пустой `CLAUDE.md` у `okna-plus`, у ряда папок несколько причин). Ограничение: одна задача на (папку, причину); выключение — остановка процесса pm2.
- U5 меняет доставку: перед слиянием — `ship-test` и `--dry-run` по `projects`, `tools`, `clients/eurosteklo`.
- `client-context` не читает `private/` и секреты: печатает только факт наличия.
