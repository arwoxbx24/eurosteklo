## Пользовательские сценарии и проверка

### История 1 — откат к утверждённому этапу по метке (приоритет P1)

Владелец или агент хочет вернуться к состоянию после этапа e1…e6. Он находит на GitHub метку `checkpoint/2026-09-30-<этап>` и открывает по ней ровно тот коммит, что записан в реестре точек отката.

**Почему P1**: без меток откат возможен только по SHA из таблицы. Облачный агент метки поставить не может.

**Независимая проверка**: список меток на GitHub сверяется с таблицей реестра построчно.

**Сценарии приёмки**:
1. **Дано** 6 строк e1–e6 в реестре, **когда** работа выполнена, **тогда** на GitHub 7 меток `checkpoint/*`, у 6 новых коммит совпадает с полным SHA строки реестра.
2. **Дано** метка `checkpoint/2026-09-30-lidy-sdelki` уже есть, **когда** работа выполнена, **тогда** она указывает на тот же коммит `575a157…`.

### История 2 — в репозитории нет мёртвой ветки (приоритет P2)

Агент, открывший список веток, не видит пустую ветку `claude/wonderful-pasteur-7tzxeu`. Её содержимое уже в `main`.

**Независимая проверка**: запрос веток GitHub по имени возвращает пусто.

**Сценарии приёмки**:
1. **Дано** ветка указывает на `575a157…` и не содержит коммитов вне `main`, **когда** работа выполнена, **тогда** ветки на GitHub нет.
2. **Дано** ветка указывает на другой коммит или содержит коммит вне `main`, **когда** агент дошёл до удаления, **тогда** удаление не выполняется, факт записан в bd.

### История 3 — выполненное поручение не висит (приоритет P3)

Новый агент при входе не получает уже выполненное поручение: в `main` нет файла сообщения и ссылки на него. Реестр точек отката сообщает, что метки поставлены.

**Независимая проверка**: поиск `SOOBSHCHENIE` по `main` пуст; в реестре только добавленные строки.

**Сценарии приёмки**:
1. **Дано** истории 1 и 2 выполнены, **когда** PR слит, **тогда** в `main` нет `docs/SOOBSHCHENIE-AGENTAM.md` и строки-ссылки в `docs/ppo/HANDOFF.md`.
2. **Дано** реестр «только дописывается», **когда** PR слит, **тогда** изменение `docs/CHECKPOINTS.md` состоит только из добавленных строк.

### Пограничные случаи

- SHA строки реестра не предок `main`: эту метку не ставить, остальные ставить, факт — в bd с выводом проверки; атом не закрывается, контрольная точка владельцу.
- Метка с таким именем уже есть на GitHub на другом коммите: не перезаписывать, стоп.
- Push отклонён второй раз: стоп, контрольная точка владельцу.
- В имени метки в таблице есть приписка «(метку ставит CLI-агент)»: имя — только текст в обратных кавычках.

- **FR-001**: На GitHub есть 6 аннотированных меток e3, e1, e2, e4, e5, e6 с именами и полными SHA из таблицы `docs/CHECKPOINTS.md` (план R1).

- **FR-005**: `docs/CHECKPOINTS.md` получает только дописанный абзац: 6 имён меток, дата 01.10, итог проверки (7 меток), отмена силы приписок «метку ставит CLI-агент»; строки таблицы не правятся (план R5).
- **FR-006**: Метки отправляются на GitHub по одной (не более 3 ссылок за push — закон репозиториев).
- **FR-007**: Изменение файлов попадает в `main` только через PR из ветки `claude/lq9-soobshchenie-vypolneno`, проверку gitleaks и слияние merge-коммитом с проверкой SHA головы.

### Ключевые сущности

- **Точка отката**: строка реестра — дата, имя метки, полный SHA, что зафиксировано, кто.
- **Метка отката**: аннотированная метка git на GitHub, имя `checkpoint/<дата>-<этап>`.
- **Разовое сообщение агентам**: файл с поручением; после выполнения удаляется вместе со ссылкой.

## Негативные примеры

- Отправить все метки одной командой `git push origin --tags` — нарушает FR-006 и может отправить локальные лишние метки.
- Удалить ветку по старому снимку `origin/*` без свежего fetch — может уничтожить коммит, пришедший после снимка (FR-003).
- Поправить строки таблицы реестра, убрав «(метку ставит CLI-агент)» — нарушает правило «только дописывается» (FR-005).
- Взять в имя метки текст ячейки целиком с припиской — метка с неверным именем.
- Удалить файл сообщения прямым push в `main` — нарушает FR-007.
