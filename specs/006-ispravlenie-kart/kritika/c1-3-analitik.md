## 3. Ферми (порядки, не точные числа)
- Вопросов: 40 точек + 5 (С25–С29) = 45. Слияние целых точек — только т.9↔С1 и, возможно, 1–3 внутри лидов (остальные дубли — на уровне «А если») → 40–44. Минус 1С-точки вне Романа (т.14, С22, №11, №37 и 1С-хвосты С9/С12/С17/С18) ≈ 4–6 → **~35–40 главных вопросов** + сейчас 161 «А если» (D Т3).
- Минут на точку: «покажите на последней сделке» (показ экрана) 3–5 мин + 2–3 «А если» по ~1 мин → **5–8 мин**. Итого 35–40 × 5–8 ≈ 3–5 ч чистого разговора.
- Встреч: при 60–90 мин фактически ~10–15 точек за встречу → **3–4 встречи с Романом** + 1–2 со знающими 1С (бухгалтерия, плановик — C §3.3). Длительность блока «Лиды» владелец ещё не назвал (журнал 28.09) — не подтверждено.
- Часы П0…П5 (агентские, с законом ТЗ: `/ce-doc-review` + `code-channel` + ≥3 блока + сборка + скриншоты ≈ 2–4 ч накладных на каждый П): П0 24 правки × 0,3–1 ч ≈ 10–25 ч; П1 ≈ 10–15 ч; П2 ≈ 5–10 ч; П3 40–45 точек × 15–30 мин поиска источника ≈ 10–20 ч; П4 ≈ 8–15 ч; П5 (липкая колонка при слоях SVG и zoom) ≈ 8–15 ч. **Итого порядок 10² ч**; П3 и П0 — самые дорогие. Реальная производительность канала не подтверждена.
- Вариантов в источниках (C §1.4, 57 строк): СОВПАДАЕТ 9 и ТОЛЬКО В ТЗ 18 → 1 вариант («так?» / «нужно?»); ТОЛЬКО НА ДОСКЕ 10 → 1 + уточнения; ПРОТИВОРЕЧИЕ 18 → 2–3 (Д/ТЗ/СМ; у точек сделок слоёв ≤ 3 по TOCHKI); НЕТ НИГДЕ 2 → 0 (открытый). Среднее ≈ 1,5 + «Другое» → **1–3 варианта на точку**, против 4 у 37 из 40 сейчас; r-tz давал 2–3 (D Т3). Чекбоксов в П4 ≈ 45 × 2,5 ≈ 10², а не 161+.

## 4. Решения и жёсткая критика
**Р1. Топ-N на первую встречу (12–15 точек), ранг = сколько разделов ТЗ закрывает ответ («Ответ закроет:») и не 1С.** Первая — С24 (модель стадий — «основа для всех остальных точек», текст карточки).
Подождите, дайте проверю: текущие «начать с этого» — лиды 3, 13, 1, 15, 14; сделки С24, С6, С9, С22, С18. Результат: т.14 и С22 — 1С, а §5 запрещает решать 1С с Романом. Значит, «начать с этого» нужно менять в том же П, иначе встреча начнётся с вопроса, на который Роман не может ответить (J3).
**Р2. Порядок по классам C §2.4 (СОВПАДАЕТ → ПРОТИВОРЕЧИЕ → ТОЛЬКО НА ДОСКЕ → ТОЛЬКО В ТЗ).**
О, я упустил: классы присвоены 57 строкам матрицы, а не 40 точкам; сопоставления «точка → класс» нет ни в spec, ни в TOCHKI. Плюс C §4д п.3: совпадение ТЗ и доски может быть не независимым (К7345 ≈ Разв. п.12). Без колонки «класс» порядок неисполним.
**Р3. Пакетирование:** 18 «ТОЛЬКО В ТЗ» — одним списком «нужно / не нужно / так и работает / не знаю» (C §2.2); сквозные «А если» (выходные, отпуск, эскалация: т.3, 13, 16, С23) — один блок «Сквозные правила».
Но что если Роман не вправе отменять пункты ТЗ (руководитель, не собственник — журнал 28.09)? Тогда «не нужно» по деньгам и 1С не финально — нужен вопрос «кто утверждает изменения процесса». И если список отдать заранее, ответ будет без показа реальной сделки — слабее; считается ли заполненный клиентом список «документом клиента» для разблокировки — не подтверждено, решает владелец.
**Р4. Одна правка на карточку: слить П2 и П3 (и текстовую часть П0.8/П1 по тем же точкам) в один проход по `tochki.html`.**
Но что если это нарушит «строго по приоритизации»? Нарушит — поэтому только как вопрос владельцу (закон согласования), не самовольно.
**Р5. В П4 — поле «таймкод видео» у точки** (и номер точки вслух на записи): транскрипт → точка без догадок (J2).
Но что если страница ответов на встрече показывается Роману через демонстрацию экрана? Тогда он видит пометки «не знает». В странице сказано «Второе окно — карта процесса», режим показа ответов не зафиксирован — не подтверждено; добавить в правила ведения «страницу ответов не демонстрировать».
**Р6. Правило владения для §2** (не меняя определения владельца): «вопрос — в процессе, где объект находится в момент события; интервал квалификация→конвертация, сделка без лида и повторный клиент — вопросы владельцу/клиенту; общее для обоих — блок «Сквозное» в лидах со ссылкой из сделок».
