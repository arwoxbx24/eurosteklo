## 4. Наблюдаемость: что есть и чего не хватает

Есть: печать числа точек и порядка при сборке; ручные проверки HANDOFF; фактчеки `FACTCHECK-*.md`. Нет ни одного утверждения (assert) и кода выхода ≠ 0.
Не хватает (одним скриптом `docs/ppo/check_ppo.py`, только чтение, выход ≠ 0 при ошибке):
1. Связность на процесс: svg-точки = карточки = `pN` = `#tN` = короткая = подробная (прототип в копии работает, 16/24 OK).
2. Свежесть склейки: `karta.svg.html` == результат `stitch.py` из A/B/C (сравнить в памяти).
3. Номера не уменьшаются: множество точек ⊇ множества на `575a157` (`git show`), новые — только > max.
4. Лиды ↔ сделки: каждый пересекающийся вопрос имеет одного владельца; во втором процессе — только ссылка; дублей = 0.
5. У каждого варианта «А если…» есть пометка источника или «наш вариант (гипотеза)».
6. ПДн = 0: телефоны/почты с исключением id Miro (длинные цифры в `<title>id Miro`); фамилии — по закрытому списку вне git (не подтверждено, что список есть в облаке).
7. Сборка дважды → те же sha256 (идемпотентность как проверка, не как надежда).

## 5. Идемпотентность

- Сборка: **да** (PROVEN, §1). Сохранить: не добавлять в HTML время сборки; ZIP (П6) собирать с фиксированной датой файлов и порядком, иначе каждая сборка меняет git.

## 6. Решения и жёсткая критика

**Р1. `check_ppo.py` (§4) обязателен в приёмке каждого П.**
Подождите, дайте проверю — не дублирует ли он существующее? Проверено: скриптов проверки в `scripts/` и `docs/ppo/` нет, только `b24_export.py`, `extract_frames.py`, сборщики. Не дублирует.
Но что если скрипт сам даёт ложные тревоги, и его начнут игнорировать? Проверено: наивный regex телефонов даёт 405 ложных. Значит, исключение id Miro — обязательная часть, иначе проверка ПДн бесполезна.
О, я упустил: скрипт — код, по закону ТЗ он тоже идёт ТЗ → `/ce-doc-review` → `code-channel`. Отдельное ТЗ «П-проверки» до П0.

**Р2. Версия формата ответов (П4)**: ключ прежний, в объект — `_v:2`; при чтении v1 `{v:"Подтвердил"}` переводить в статус v2, неизвестные поля не удалять; `.md` с шапкой формата; импорт — замена по номеру.
Подождите, дайте проверю — а есть ли вообще ответы в браузерах? Не подтверждено: транскрипта нет, запись о показе нет. Миграция стоит дёшево, потеря — необратима; оставить.
Но что если клиент/владелец открывает страницы из разных папок (file://)? Происхождение (origin) localStorage для file:// в разных браузерах разное — не подтверждено. Вывод: единственная надёжная копия — выгруженный `.md`; перед выкладкой П4 попросить владельца «Сохранить ответы» на старой версии.

**Р3. Откат = один П — один PR с merge-коммитом**; точка отката перед П0 уже есть (`575a157`, метка на origin) — новую строку не нужно, нужна ссылка на неё в spec.
О, я упустил: revert П4 не откатывает данные в браузере (§3). Поэтому П4 — последним из правок общего кода не делать: сначала Р2 (чтение обоих форматов), потом смена интерфейса.

**Р4. Флаг на процесс в `Proc` (например, `answers_v2`)**, чтобы П4/П5 включать сначала на сделках.
Но что если это противоречит Т4 и одинаковости страниц? Да: две разные системы ответов на одной встрече путают. И флаги в общем коде — долг. Оценка низкая; оставить только как запасной вариант, если владелец не даст «да» на правку лидов.

**Р5. `build_all.py`: вызывать `stitch.py` и выходить с кодом ≠ 0 при пропущенном процессе.**
Подождите, дайте проверю — ломает ли вызов `stitch.py` идемпотентность? Проверено: `stitch.py` дважды → тот же `karta.svg.html` (sha256). Не ломает. Правка `build_all.py` — общий файл (регламент П6): одна сессия.

**Р6. Публикация**: не публиковать и не обещать «поверх ссылки», пока владелец не назовёт объект.
Но что если владелец ждёт ссылку? Тогда это новая ссылка — только по его «да» и с записью в `LINKS.md`.
