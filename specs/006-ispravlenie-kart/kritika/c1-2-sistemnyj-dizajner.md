## 2. ADR

**ADR-1. Новые точки С25+ без перенумерации.** *Контекст:* клиент видел С1…С24. Номер N — это одновременно `id="tN"`/`pN`, ключ ответа в localStorage и ссылка «С7» в выгрузке `.md`. *Решение:* номера только добавляются. Объединённая точка остаётся «надгробием»: карточка с `id="tN"` и текстом «объединено с т. M →», на карте точка тоже остаётся (иначе `#pN` молча не сработает: `fromHash` без цели ничего не делает). *Альтернативы:* (а) перенумеровать по ходу процесса: ломаются память клиента, якоря и сохранённые ответы; (б) подномера «С7.1»: `BP` разбирает `Точка (\d+):` и `^#p(\d+)$`, поэтому «7.1» превратится в 7 и будет коллизия; (в) скрытые строковые ID и видимый номер отдельно: надёжно, но нужен перевод всего `BP`. *Последствия:* номер ≠ порядок процесса. В навигаторе С25+ встанут в конец своей группы слоя, это допустимо. Нужен реестр «номер навсегда» в `TOCHKI.md`.
**ADR-2. Ответы: чекбоксы, импорт и экспорт `.md`.** *Контекст:* сейчас на точку 3 радиокнопки и одно поле. Запись `{v,t}` хранится по ключу `evro-<slug>-answers`. «А если…» и «Ещё» не сохраняются. Выгрузка — текст для человека в порядке `top5`, без slug и версии; разобрать её обратно нельзя. *Решение:* localStorage = автосохранение черновика. Переносит ответы только `.md`: читаемый текст + машинный блок в конце (```` ```otvety-json ````) со схемой `{proc, build, date, points:{N:{st, var:[id], ifs:[i], extra, note, qhash}}}`. `build` — хэш `tochki.html`, `qhash` — хэш текста вопроса. Импорт: slug должен совпасть, иначе отказ. Если отличается `build` или `qhash`, ответ помечается «вопрос изменился после ответа». Показывается отчёт «принято N, пропущено M». Текст вставляется только через `textContent`. Файл ответов хранится только в `client-materials/private/<дата>-vstrecha/`, в git не попадает. *Альтернативы:* (а) оставить как есть — данные теряются, импорта нет; (б) чистый `.json` — удобно машине, но владелец просил `.md`; (в) серверное хранилище или БД артефакта — новая ссылка и выход за контур, запрещено. *Последствия:* ID вариантов обязаны быть стабильными, поэтому П3 (варианты по источникам) действительно должен идти до П4. Старые записи `{v:"Подтвердил"|"Иначе"|"Не знает", t}` нужно перенести в новый формат.
**ADR-3. Закреплённая колонка ролей.** *Контекст:* у сделок 3 слоя друг под другом с **разными** дорожками (А — 7, Б — 7, В — 0). `ZM` масштабирует SVG по ширине, а значит, и по высоте. У сделок подписи дорожек без разметки: в `karta-A.svg.html` это просто `rect x=0 width=170` + `text`, `class="lane-h"` = 0. У лидов `lane-h` есть, `x=20`. *Решение:* подписи остаются в SVG в группе `<g class="lanes">` каждого слоя. При `scroll` в `.mapwrap` скрипт сдвигает эту группу на `scrollLeft / масштаб`. Геометрия общая со схемой, поэтому при любом масштабе расхождение = 0. Вопрос «кто за что отвечает» решается на сборке: узел относится к дорожке, если попадает в её полосу по Y. *Альтернативы:* (а) HTML-колонка `position:sticky`, как написано в spec: второй источник геометрии, при масштабе высоты дорожек надо пересчитывать, при стыке слоёв колонка должна меняться; (б) клон SVG-среза 0…170 со sticky: геометрия та же, но `ZM` должен масштабировать два SVG. *Последствия:* правка контракта (`class="lanes"`, `data-role`), правка `ST` (группа внутри `translate` слоя допустима), подложка подписи непрозрачная.

## 4. Решения и жёсткая самокритика
**Предлагаю:** ADR-1 + ADR-2 + ADR-3; assert связности в `BP` вместо ручных проверок HANDOFF; метку сборки на всех страницах.
*Подождите, дайте проверю…* работает ли уже `karta.svg.html` как источник для П0. **Проверка:** временная пересборка `ST` даёт файл байт в байт. Значит, источники — только `karta-A/B/C`, и в spec это надо написать, иначе исполнитель поправит склейку и потеряет правку.
*О, я упустил…* что ссылки для публикации нет. **Проверка:** в `LINKS.md` только v1–v5, drawio и `tgf`; `karta-sdelki` там нет. Пункт spec §4.4 «поверх той же ссылки» неисполним. Нужно «да» владельца: какой объект считается «той ссылкой», или публикация папкой (П6).
*Но что если…* sticky-группа внутри SVG закроет узлы у левого края? **Проверка:** из точек у сделок в полосе только С24, `y=120`; дорожки начинаются с `y=140`, так что точку группа дорожек не накроет. Узлы доски левее `x≈190` не проверял — **не подтверждено**.
*Подождите, дайте проверю…* хватит ли `qhash`, если П3 меняет состав вариантов. **Проверка:** варианты сейчас — `<li>` без ID (`BP`: `ifs` — текстовый список). Нужны явные ID вариантов в `tochki.html`, иначе чекбокс «var:[2]» после П3 укажет на другой вариант. Моё ADR-2 без этого дырявое: ID вариантов — обязательное поле П3.
*О, я упустил…* ответы встречи 29.09. **Проверка:** транскрипта нет. Были ли ответы в localStorage владельца, в проекте не записано — **не подтверждено**. Миграция `{v,t}` нужна на случай, если были.
*Но что если…* сделать архив П6 — рискованно? **Проверка:** ссылки относительные (D, Т1), внешняя зависимость одна — шрифт. Архив рабочий, но после распаковки в новую папку localStorage в не-Chromium браузерах, вероятно, окажется пустым (**не подтверждено**) — это закрывает импорт `.md`.
**Слабые места моих решений:** ADR-3 — это JS-трюк. При печати и без JS подписи остаются слева в SVG, так что деградация мягкая, но spec обещала «вне SVG». Разница со словами владельца — вынести ему на «да». Машинный блок в `.md` владелец может счесть «шумом» — свернуть в конец.
