# Инструкции проекта «Евро стекло»

## Назначение

Этот проект централизованно хранит клиентские материалы по ранее начатой интеграции с Битрикс24 после смены руководства компании.

## Текущий режим

- Прямое указание владельца 28.09.2026: «мы будем разрабатывать спецификации, документы, бизнес-процессы, технические задания по данным, которые у нас есть».
- Разрешено: анализ материалов, выгрузка CRM только чтением, спецификации, документация бизнес-процесса, ТЗ, подготовка вопросов к клиенту.
- Не реализуем интеграцию и не меняем Битрикс24 без отдельного указания владельца.

## Исходные данные

- Клиент прислал mind map (доска Miro, узлы на русском) с бизнес-процессом.
- Описание может использовать нестандартную структуру и термины; нормализация разрешена указанием владельца 28.09.2026 с сохранением исходной формулировки и источника.
- Ранее интеграция уже разрабатывалась; нельзя считать текущие материалы проектом с нуля.
- После смены руководства прежние решения считаются гипотезами, пока они не подтверждены актуальными материалами.
- Видео не содержит слышимого звука и не является источником речи.
- CSV использовать как основной структурный источник, а пять JPG-скриншотов — как дополнительные материалы для будущей склейки процесса.

## Правила работы

1. Канонический корень — эта директория; не разносить контекст по соседним проектам.
2. Конфиденциальные оригиналы хранить только в `client-materials/private/`; не коммитить и не публиковать их.
3. Оригиналы не редактировать. Производные документы создавать в `docs/` с указанием источника и даты.
4. Отделять факты клиента от интерпретаций агента: `PROVEN`, `INFERRED`, `UNVERIFIED`, `CONTRADICTED`.
5. Оригинал mind map не перестраивать; выводы из неё — только в производных документах `docs/` с меткой и источником.
6. При склейке процесса сверять CSV, JPG, доску Miro и выгрузку Б24; расхождения сохранять, а не угадывать.
7. Не добавлять функции интеграции и требования, которых нет в источниках клиента.
8. Не помещать в Git ключи, пароли, персональные данные, выгрузки CRM и иные закрытые данные.

## Git: ветки, синхронизация, откат (владелец 30.09.2026)

Полный регламент — `docs/specifications/2026-09-30-git-collaboration.md` (П1–П11); точки отката — `docs/CHECKPOINTS.md`; идеи агентов — `docs/idei/<агент>/`.

1. Ствол — `main` (ветка по умолчанию, владелец переключил 30.09). Старые ветки `codex/8b44-eurosteklo` и `claude/wonderful-pasteur-7tzxeu` — архив: не писать, не двигать, не удалять.
2. Каждая сессия — своя ветка от свежей `origin/main`: Codex CLI — `codex/<ГГГГ-ММ-ДД>-<суть>`, Claude CLI — `claude-cli/<ГГГГ-ММ-ДД>-<суть>`, Claude Web — ветка от платформы. В чужую ветку не писать. Автор коммитов — своё имя: `git config user.name "Codex CLI"` / `"Claude CLI"` / `"Claude Web"`.
3. Начало сессии: `git status` (чисто) → `git fetch origin` → `git switch -c <ветка> origin/main`. Прочитать этот файл, `docs/ppo/HANDOFF.md`, журнал решений, `docs/CHECKPOINTS.md`, свежие `docs/idei/*/`.
4. Конец сессии: `git diff --check`, поиск ПДн = 0, сборка `python3 docs/ppo/build_all.py` (если трогали `docs/ppo`) → push своей ветки → PR в `main` → слияние merge-коммитом (не squash, не rebase) самим агентом. Клиентские документы (`docs/ppo/**` кроме `HANDOFF.md`, ТЗ, карты) сливаются только после «да» владельца.
5. Мозговой штурм: каждый агент пишет только в свою `docs/idei/<агент>/`, читают все; в клиентские документы — только после «да» владельца.
6. Общие файлы (`AGENTS.md`, `CLAUDE.md`, HANDOFF, журнал решений, `sanitized-*`, `docs/ppo/_common/`, `CHECKPOINTS`) правит одна сессия за раз; журнал и реестр — только дописывать. Конфликт в собранных HTML — решать в `_parts/` и пересобирать.
7. Параллельные блоки одной сессии (закон дробления) пишут разные файлы в одном дереве — разрешено; две разные сессии в одну ветку — запрещено.
8. Точка отката — строка в `docs/CHECKPOINTS.md` (полный SHA) + метка `checkpoint/<ГГГГ-ММ-ДД>-<этап>` (ставит CLI-агент; первая метка `checkpoint/2026-09-30-lidy-sdelki` уже опубликована). Метки не двигать. Откат — только `git revert` новым PR; force-push и переписывание истории `main` запрещены (исключение — удаление ПДн по решению владельца).
9. Старые копии с историей до чистки 29.09: ничего не пушить и не вливать; `git branch backup/<дата>-old HEAD` (только локально, не пушить — там ФИО) → `git fetch origin` → `git switch -c <ветка> origin/main` → свои правки переносить вручную с проверкой ПДн.
10. Вне Git: `client-materials/private/`, база Beads, выгрузки CRM, ключи — передаёт владелец отдельно.
11. Этот раздел касается только Git: закон ТЗ, RG-001 и остальные законы действуют без изменений.

## Закон блокировки: нет источника — нет утверждения (владелец 28.09.2026)

Агент — помощник клиента, не владыка его процессов: неверный процесс = ущерб архитектуре клиента.
1. Каждое утверждение в документе (процесс, роль, поле, срок, интеграция, 1С) — с меткой `PROVEN|INFERRED|UNVERIFIED` и источником (файл, узел/комментарий Miro, ID сделки, строка видео/документа клиента).
2. Нет источника → пишется «Информации нет» и вопрос в раздел «Вопросы к клиенту»; гипотетический процесс не строится. `INFERRED` — только из двух и более источников, с их перечнем.
3. Пункт без ответа клиента = БЛОКИРОВАН: не переходит в ТЗ, регламент и настройку. Разблокирует только документ клиента (видео, регламент, ответ на встрече), сохранённый в `client-materials/private/` и внесённый в `INVENTORY.md`.
4. Перед выдачей документа клиенту — проверка противоречий в 3 круга: (а) источник каждого утверждения; (б) сверка документа с другими документами `docs/` и источниками; (в) критик-рецензент (навык рецензии) — находки закрыты или вынесены в вопросы.
5. Навыки проекта — `.claude/skills/` (только этот проект); вызываются явно, текст навыка — справка, не замена этому закону.

## Разрешённый результат текущего этапа

- перечень полученных файлов без пересказа содержимого;
- источник и дата получения каждого материала;
- отметка о конфиденциальности и целостности файла.

2. Сверить и склеить её с `Евростекло.csv` и всеми пятью JPG-скриншотами.
3. Сохранить найденные расхождения и пробелы без догадок.
4. На основе объединённого источника написать документацию по бизнес-процессу.
